## 三、方案（零 DDL）

### 3.1 结算点：`point_lock_user()`（`my_func.inc.php:1380-1385`）

| 维度 | 放 `point_apply_change` 负分支 | 放 `point_lock_user` |
|---|---|---|
| 覆盖消费路径 | 4 处扣减 | 4 处（`point_apply_change:1422` 自动包含） |
| 入口改动 | 0 | 0 |
| 预检余额正确性 | 错（用过期的数比对，订单号已生成才失败） | 对（锁后、比对前） |
| 锁序 | 需自行保证在 `FOR UPDATE` 后 | 天然在锁后 |

并发安全：第二个请求阻塞在 `FOR UPDATE`，获锁后读到已扣减的 `point`，推导出的过期额为 0。幂等自证，无需状态位。

`point_lock_user()` 的 docblock 由「加锁返回余额」改为「加锁、结算过期、返回可花费余额」。

### 3.2 推导算法

1. 取 `point_lock_user` 已读到的 `point`，读 `point_recharged`；`G = max(0, point - point_recharged)`。
2. 查 `point_log`：`user_id = ? AND change_point > 0`，按 `create_time ASC`；用 `point_is_recharged_type(type, change_point)` 过滤出赠送批次。**该谓词与 `point_apply_change:1441` 共用同一函数，是充值规则的精确补集**，新增任何不涨 `point_recharged` 的正数流水自动成为赠送批次。
3. `consumed = max(0, SUM(赠送批次) - G)`（钳位见 3.5）；自最老批次起扣减 `consumed`，余额即「存活批次」。
4. 存活批次中 `DATE_ADD(create_time, INTERVAL 3 MONTH) <= NOW()` 的部分求和（**无存量豁免**，早于上线日发放的历史批次同样参与判定）。
5. `expired = min(第4步结果, G)`。
6. `expired > 0` 时：`UPDATE users SET point = point - expired`（`point_recharged` 不动）+ `point_add_log(..., -expired, ..., POINT_LOG_TYPE_EXPIRE, ...)`，返回扣减后的余额。

三个实现约束：
1. **不嵌套事务**：结算走「纯计算 + 内联 UPDATE/写日志」，不调 `point_tx_begin/commit`（`my_func.inc.php:1334-1347` 的 `inTransaction()` 只防重复 begin，不防提前提交外层事务）。
2. **不递归**：写日志直接调 `point_add_log()`，不回调 `point_apply_change()`。
3. **锁序**：结算的 `UPDATE users` 在 `point_lock_user()` 的 `FOR UPDATE` 之后。

### 3.3 到期口径

`expire_time = DATE_ADD(create_time, INTERVAL 3 MONTH)`（自然月，8/31 → 11/30）。改固定 90 天只需把 `MONTH` 换 `DAY`。

### 3.4 无存量豁免（已确认，用户决定）

原方案曾设 `POINT_GIFT_RULE_START` 上线日地板，豁免早于上线日发放的赠送批次（理由是 `db/V2.10:3` 把 V2.10 之前的存量余额一律记为赠送）。**已取消**：所有赠送积分一律按各自发放日 +3 自然月判定，存量赠送同样过期。

**上线影响（必须提前知情）**：上线瞬间，所有 `create_time + 3 MONTH <= NOW()` 且尚未被消耗的赠送批次会被一次性扣除。用下面的 SQL 预估规模，其中 `expired_estimate` 是上界（未扣减 FIFO 已消耗部分）：

```sql
-- 上线前预估：每个用户按「赠送批次总额中已过期部分」估算将扣多少（上界）
SELECT u.user_id, u.point, u.point_recharged, u.point - u.point_recharged AS gift_balance,
       COALESCE(l.expired_sum, 0) AS expired_estimate
FROM users u
LEFT JOIN (SELECT user_id, SUM(change_point) AS expired_sum
             FROM point_log
            WHERE change_point > 0
              AND type NOT IN (1, 3)                       -- 非充值钱包 = 赠送批次
              AND DATE_ADD(create_time, INTERVAL 3 MONTH) <= NOW()
            GROUP BY user_id) l ON l.user_id = u.user_id
WHERE u.point - u.point_recharged > 0
ORDER BY expired_estimate DESC;
```

真实扣减额受 FIFO 已消耗归属影响，实际 ≤ `expired_estimate`，且不会让余额为负（3.5 的护栏 + `expired ≤ G` 钳位）。

**上线日不再是配置项**：`POINT_GIFT_RULE_START` 常量已从代码中删除，无需在上线前改任何日期。

### 3.5 账本不完整时的降级

推导依赖「`point_log` 完整记录每笔赠送、`users.point` 只经 `point_apply_change` 变动」。存在绕过写入口的手工加分（`db/clearup_zezhang_game_orders.sh:75`）时 `SUM(赠送批次) < G`，无法判定哪些批次已被消耗。

**实现取 `SUM < G` 即整体放弃结算**（`my_func.inc.php` 的 `_point_gift_alive_batches()`）：返回空存活批次 → 不做过期扣减。降级方向是「不扣」，不会误扣用户积分。

测试环境实测命中该护栏：`test`（G=110，已记录赠送发放 10）、`test_user_low_point_1788749476`（G=30，已记录 0）两个用户被挡下，未被扣减。

## 五、上线前置条件：充值卡钱包人工修正

### 5.1 背景

`db/V2.10_20260914_course_share_reward.sql:8` 执行 `ADD COLUMN point_recharged INT NOT NULL DEFAULT 0`，**所有存量行的 `point_recharged` 被置 0**，含 V1.9（2026-06-07）到 V2.10（2026-09-14）之间买卡换来的付费积分。接上过期逻辑后这批积分会被判成赠送并到期扣光。

面额依据：`point_card` 无金额列，每张固定 `POINT_CARD_VALUE = 10`（`my_func.inc.php:1301`）。V2.10 落地日 2026-09-14（`db/RELEASE_STEPS.md:31`）。

### 5.2 处理方式

**按用户手工执行，不落库为仓库归档文件**（用户决定）。逐用户 SQL：

```sql
SET @uid := '待处理用户ID';
SET @v210_date := '2026-09-14 00:00:00';

-- 核对卡明细与面额（预期 cards 与手工名单一致）
SELECT COUNT(*) AS cards, COUNT(*) * 10 AS card_value
FROM point_card
WHERE status = 1 AND redeem_user_id = @uid AND redeem_time < @v210_date;

-- 修正：封顶在 point，保证 G = point - point_recharged 非负
UPDATE users
SET point_recharged = LEAST(point, point_recharged + (
      SELECT COUNT(*) * 10 FROM point_card
      WHERE status = 1 AND redeem_user_id = @uid AND redeem_time < @v210_date))
WHERE user_id = @uid AND point_recharged < point;

-- 核对
SELECT user_id, point, point_recharged, point - point_recharged AS gift_balance
FROM users WHERE user_id = @uid;
```

两条约束：
- **`redeem_time < @v210_date` 不可省**：V2.10 之后的卡兑换已正确计入 `point_recharged`（`my_func.inc.php:1441`），重复补发会把赠送积分吃成充值。
- **`LEAST(point, ...)` 不可省**：用户已消费的部分不存在，`point_recharged` 涨过 `point` 会让 G 变负。

### 5.3 已完成记录

| 用户 | 修正前 | 修正后 | 说明 |
|---|---|---|---|
| `13005460886` | `point=12, point_recharged=0` | `point=12, point_recharged=12, gift_balance=0` | 5 张卡（id 23-27，2026-09-03 兑换）共 50 分；按封顶法余额全部归入充值钱包 |

### 5.4 剩余名单判定

```sql
SELECT u.user_id, u.point, u.point_recharged, v.card_value, v.cards
FROM users u
JOIN (SELECT redeem_user_id, COUNT(*) AS cards, COUNT(*) * 10 AS card_value
      FROM point_card
      WHERE status = 1 AND redeem_user_id IS NOT NULL
        AND redeem_time < '2026-09-14 00:00:00'
      GROUP BY redeem_user_id) v
  ON v.redeem_user_id = u.user_id
WHERE u.point_recharged = 0 AND u.point > 0
ORDER BY u.point DESC;
```

返回空即处理完毕。判据：处理过的用户只要 `point > 0`，`LEAST` 结果必然大于 0；`point = 0` 的用户无可保护余额。

### 5.5 已知绕过点

`db/clearup_zezhang_game_orders.sh:75` 直接 `UPDATE users SET point = point + $TOTAL_POINTS`，绕过唯一写入口。该脚本在 `:84` 同时写了一条正数 `type=6` 流水，不变量 `G ≤ SUM(赠送批次)` 保持，推导不会算崩；但退款会被当成**全新赠送批次，从退款日起算 3 个月**。修法（只动该脚本）：同步 `point_recharged`，或改为调用 `point_apply_change()`。
